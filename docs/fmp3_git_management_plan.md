# リリース済み FMP3 カーネル Git 管理計画

## 0. 要約（決定事項）

| 項目 | 方針 |
|------|------|
| リポジトリ性格 | リリース成果物のアーカイブ（開発は内部SVNのまま）。全ターゲットの**和集合を1本のツリー**で保持するモノレポ型 |
| ブランチ | **メジャーバージョン M 毎**（`release/3.M`）。新メジャーは前メジャーの tip から分岐 |
| コミット順序 | 全リリース（個別＋簡易）を**日付昇順で直列化**。author/committer date をパッケージ日付に固定 |
| ターゲット非依存部 | **個別パッケージから取り込む**（簡易パッケージからは取り込まない）。タグ `v3.M.N` |
| ターゲット依存部 | **簡易パッケージから取り込む**。タグ `<target>_<tool>-<date>`（例 `polarfire_soc_kit_gcc-20241224`） |
| 上書き防止 | 簡易パッケージ取込時に**非依存部パスを除外**＋**日付順取込**の2重ガード |
| 派生版対応 | 本アーカイブを派生版（`fmp3_core`：CMake + Python cfg）の **pristine 上流**とみなす。派生版は別リポジトリで、アーカイブのタグ/コミットを **submodule 等で pin**。アーカイブは pristine 厳守（派生版固有ファイルを混入させない） |

---

## 1. 目的と前提

- 目的：TOPPERS で公開済みの FMP3 カーネル（個別パッケージ／簡易パッケージ）を Git 上で再構成し、リリースの追跡・差分確認・パッケージ復元を可能にする。
- 前提：本流の開発は内部 SVN。この Git リポジトリは **公開済みリリースのアーカイブ**であり、SVN の全履歴移行ではない。
- バージョン `3.M.N`
  - `M`（メジャー）：依存部の変更が必要な非依存部変更で上がる
  - `N`（マイナー）：依存部の変更が不要な非依存部変更で上がる
  - → **同一メジャー内では、非依存部が N を進めても依存部は互換**。これがブランチ境界の根拠。

---

## 2. 全体モデル

リポジトリを「特定ターゲットのパッケージ」ではなく「**全ターゲットの成果物の和集合**」として扱う。

```
release/3.M ブランチ（時系列で直列コミット）
  ● v3.M.0            個別パッケージ（非依存部）取込
  ● target_A ... -D1  簡易パッケージ（依存部）取込・タグ
  ● target_B ... -D2  簡易パッケージ（依存部）取込・タグ
  ● v3.M.1            個別パッケージ（非依存部）更新
  ● target_A ... -D3  簡易パッケージ（依存部）更新・タグ
  ...
```

- **非依存部**（カーネル本体＋cfg）は個別パッケージ由来。時点ごとに `v3.M.N` タグを付与。
- **依存部**（`./arch/<core>/<chip>` ほか）は簡易パッケージ由来。パッケージ毎に `<target>_<tool>-<date>` タグを付与。
- 任意のタグをチェックアウトすると、その時点の非依存部＋その時点までに取り込んだ全依存部が存在する（後述の復元手順で対象ターゲットの部分木だけ抽出）。

---

## 3. ファイル分類マニフェスト（最重要）

「非依存部」と「依存部」をパスで機械的に判定できるようにする。これが上書き防止の根幹。

`tools/indep_paths.txt`（非依存部の許可リスト。実レイアウトに合わせて調整）:

```
# ターゲット非依存部（カーネル本体 + cfg）。ここに列挙したパスは
#   - 個別パッケージ取込 : この集合のみ rm+copy（削除も反映）
#   - 簡易パッケージ取込 : この集合を除外（＝上書きしない）
kernel/
include/
syssvc/
library/
cfg/
```

- 依存部＝上記以外（`arch/` 配下のコア共通・チップ固有、`target/` 等）。
- 依存部の内部階層：
  - `arch/<core>/<chip>/` … チップ固有（そのターゲット専用）
  - `arch/<core>/` … コア共通（同コアの複数チップで**共有**）
  - `arch/` 直下 … アーキ共通（**共有**）
- 「共有」ファイルが後述の上書き問題の対象になる。

---

## 4. ブランチ戦略

- ブランチ名：`release/3.M`（例 `release/3.1`, `release/3.2`）。
- 新メジャー `3.(M+1)` は **前メジャー `release/3.M` の tip から分岐**。
  - 理由：メジャー更新は非依存部・依存部の協調変更。前 tip から分岐すると `git diff release/3.M release/3.(M+1)` でメジャー間差分が読める。
  - 分岐直後の最初のコミットが `v3.(M+1).0`（非依存部）。以降、依存部は各ターゲットの簡易パッケージが日付順にトリクルインする。
  - レイアウトが大幅に変わった場合のみ orphan ブランチ化も可（→ §11 要確認）。
- default ブランチ：最新メジャーの `release/3.M` を指す（または `main` を最新メジャーへ追従）。

---

## 5. コミット／タグ運用

### 5.1 日付順コミットの厳守（注意点への対応）

- **理由1（共有ファイルの上書き）**：簡易パッケージは非依存部・コア共通・アーキ共通を共有する。日付が前後してコミットすると、古い版の共有ファイルが新しい版を上書きし、ブランチ tip が過去状態に退行する。
- **理由2（履歴の単調性）**：日付順であれば `git log` / `git blame` / タグ間 diff がすべて「前進」を表し、意味を持つ。
- 実装ガード：取り込みスクリプトが「新パッケージ日付 < 直近コミット日付」を検出したら中断する（§7）。

### 5.2 コミット日付

- `GIT_AUTHOR_DATE` / `GIT_COMMITTER_DATE` を**公開パッケージと同じ日付**に固定（例 `2024-12-24T00:00:00 +0900`）。
- これで `git log` の時系列＝リリース時系列が一致する。

### 5.3 コミットメッセージ規約

```
Import individual package (target-independent) v3.M.N (YYYYMMDD)
Import simple package <target>_<tool> (YYYYMMDD)
```

### 5.4 タグ規約（annotated tag）

| 対象 | タグ名 | 例 |
|------|--------|-----|
| 非依存部（個別P） | `v3.M.N` | `v3.1.0` |
| 依存部（簡易P） | `<target>_<tool>-<date>` | `polarfire_soc_kit_gcc-20241224` |

タグメッセージに版・日付・元パッケージ名を残す（トレーサビリティ）。

## 6. 取り込みワークフロー

1. リリース全件（個別＋簡易）を**日付昇順に整列**した一覧を作る（§8 のマニフェスト）。
2. 上から順に：
   - **個別パッケージ**：非依存部（`indep_paths.txt` の集合）を **rm+copy**（削除ファイルも反映）→ commit → `v3.M.N` タグ。
   - **簡易パッケージ**：非依存部を**除外**して依存部を overlay → commit → `<target>_<tool>-<date>` タグ。
3. メジャーが上がる箇所で新ブランチを切る（§4）。

> 依存部のソースは簡易パッケージを主とする。個別パッケージの「依存部まとめ」は、簡易パッケージ未提供ターゲットの補完としてのみ任意利用（同一ファイルで競合する場合の優先順位は要確認 → §11）。

## 7. 取り込みスクリプト（スターター）

`tools/import_fmp3.sh`（本計画に同梱）。要点のみ抜粋：

```bash
# 個別パッケージ（非依存部）
tools/import_fmp3.sh indep  --date 20240701 --version 3.1.0 pkg_fmp3-3.1.0.tar.gz

# 簡易パッケージ（依存部のみ、非依存部は自動除外）
tools/import_fmp3.sh simple --date 20241224 \
    --target polarfire_soc_kit --tool gcc \
    polarfire_soc_kit_gcc-20241224.tar.gz
```

スクリプトが実施すること：
- 直近コミット日付との**日付順チェック**（過去なら中断）。
- `indep` … `indep_paths.txt` の各パスを rm+copy（削除反映）。
- `simple` … `indep_paths.txt` を除外して overlay（非依存部を触らない）。
- コミット日付を `--date` に固定し、規約通りのメッセージ＋annotated tag を付与。

エッジケース（スクリプトのコメントにも明記）：
- **同一ターゲットの再リリースでファイルが削除された場合**：overlay では消えない。当該ターゲット固有ディレクトリ（`arch/<core>/<chip>/`, `target/<board>/`）に限り rm+copy するオプションを用意する（他ターゲットの共有ファイルは消さない）。
- 共有ファイルの削除は稀。発生時は手動で確認・調整。

## 8. リリース一覧マニフェスト

`RELEASES.csv` で全リリースと Git 対応を台帳化：

```csv
date,type,version,target,tool,package,branch,tag
20240701,indep,3.1.0,,,pkg_fmp3-3.1.0.tar.gz,release/3.1,v3.1.0
20241224,simple,,polarfire_soc_kit,gcc,polarfire_soc_kit_gcc-20241224.tar.gz,release/3.1,polarfire_soc_kit_gcc-20241224
...
```

- 取り込みの入力（＝処理順）と、監査・再構築の索引を兼ねる。
- `date` でソートした順にスクリプトへ流す運用にすると、日付順が自動担保される。

## 9. パッケージ復元と検証

### 9.1 簡易パッケージの復元

```bash
git checkout polarfire_soc_kit_gcc-20241224
# 非依存部（indep_paths.txt）+ 当該ターゲットの依存部部分木 を抽出してアーカイブ
```

- 復元は「非依存部＋そのターゲットの依存部」を取り出す。タグ時点のツリーには他ターゲットの依存部も含まれるので、抽出時に対象外を落とす。

### 9.2 検証（QA）

- 取り込み直後に、Git 復元物と**元 tarball を diff** して一致を確認。
- 特に**非依存部の一致**を必ず確認：ズレがあれば「簡易Pがその時点の個別Pと異なる非依存部を同梱していた／間にマイナー版があった」というシグナル。原因を切り分け、必要なら `v3.M.N` の取込時点を調整。

## 10. リポジトリ設定

- `.gitattributes`：**バイト完全保持**のため改行変換を無効化。
  ```
  * -text
  ```
  （Windows/WSL2/Cygwin 混在環境での CRLF/LF 事故と、元配布物とのハッシュ不一致を防ぐ）
- `.gitignore`：ビルド生成物のみ（アーカイブなので基本は何も無視しない方針でも可）。
- 命名・タグ・メッセージ規約は本書 §5 に集約し、`CONTRIBUTING`/`README` から参照。

## 11. 将来の派生版（`fmp3_core`：CMake + Python cfg）への対応

### 11.1 背景と位置づけ

参考：`asp3_core`（TOPPERS/ASP3 3.7.2 ベースの改変版）は、
- CMake 一本化（`cmake --preset` で cfg 3パス〜ELF まで自動）
- cfg の Python 化・TECS レス（プレーンC）
- `kernel/` は **PRISTINE** 維持、上流との乖離を `DIVERGENCE_MAP.md` で台帳管理
- `UPSTREAM_VERSION` / `UPSTREAM_PRISTINE.txt` で上流バージョン・コミットを固定参照
- 上流は**手動マージで追従**

という構造をとっている。FMP3 でも同型の派生版（仮 `fmp3_core`）を作るなら、**本アーカイブリポジトリが派生版の「上流（pristine mirror）」になる**。したがってアーカイブ側を、派生版が安全に pin・追従できる形に整えておく。

### 11.2 設計原則

1. **アーカイブは常に pristine**。CMake・Python cfg・エージェント設定（`AGENTS.md`/`.clinerules` 等）・`DIVERGENCE_MAP.md` などの**派生版固有ファイルを絶対に混入させない**。派生版は必ず**別リポジトリ**（`fmp3_core`）。
2. **アーカイブのタグ/コミットを pin 対象にする**。派生版は `fmp3_core/` に**アーカイブを submodule（将来）／subtree／vendor 取込**として、特定タグまたはコミットを固定参照する。
3. **ディレクトリレイアウトは TOPPERS 標準を維持**（`kernel/ include/ syssvc/ library/ cfg/ arch/ target/ …`）。派生版がクリーンにマッピング・オーバレイできることが前提。`asp3_core` の pristine 由来ディレクトリ（`arch cfg doc include kernel library sample syssvc target test utils`）と揃えると移行が楽。
4. **`cfg`・`kernel` は非依存部としてアーカイブに原本を保持**（原 cfg のまま）。Python cfg 化・CMake 化は**派生版側でオーバレイ／置換**し、置換分は派生版の `DIVERGENCE_MAP.md` に記録。→ §3 の `indep_paths.txt` に `cfg/` を含める方針と整合。

### 11.3 pin 契約（派生版が何を固定参照するか）

| 参照対象 | アーカイブ側の識別子 | 派生版側の記録先（`asp3_core` 相当） |
|----------|----------------------|--------------------------------------|
| 非依存部バージョン（一次参照） | `v3.M.N` タグ | `UPSTREAM_VERSION` |
| 全ツリーの固定点 | コミットハッシュ（任意で `snapshot/3.M.N` タグ併設） | `UPSTREAM_PRISTINE.txt` |
| ターゲット依存部（採用分のみ） | `<target>_<tool>-<date>` タグ | `DIVERGENCE_MAP.md` / 移植記録 |

- 派生版が対応するのは全ターゲットの部分集合で良い（`asp3_core` も7ターゲット）。アーカイブの accumulation ツリーから必要ターゲットだけをマッピングすればよく、pin は基本「非依存部 `v3.M.N` ＋（必要なら）コミットハッシュ」で足りる。

### 11.4 上流追従フロー（派生版側）

1. 新 FMP3 リリース → アーカイブを取込・タグ付け（§6〜§8）。
2. 派生版の pin を bump（submodule 更新 or `UPSTREAM_*` 更新）。
3. 手動マージ。非依存部の差分は `v3.M.N` 間 diff、依存部は該当ターゲットタグ間 diff で確認。
4. `DIVERGENCE_MAP.md` を更新し、CI（`asp3_core` 同様、QEMU 複数機種＋ホスト）で回帰。

### 11.5 アーカイブ側で追加で守るルール（pin 契約の担保）

- 各 pin 点で**全ツリーが整合**（accumulation モデルで担保。§2）。
- **タグ名は不変**：リネーム・削除禁止（派生版の pin が壊れる）。
- 依存部の**共有ファイルは日付順コミット厳守**（派生版のマージ差分を単調に保つ）。§5.1 と同根拠。

## 12. 要確認事項

1. **新メジャーの分岐元**：前メジャー tip から分岐（履歴連続）で良いか、レイアウト激変時は orphan とするか。
2. **依存部ソースの優先順位**：同一ターゲット・同一日付で簡易Pと個別P依存部が両方ある場合、どちらを正とするか。
3. **非依存部タグ `v3.M.N` の付与**：本計画では推奨・付与前提。不要なら簡易Pタグのみに簡素化可。
4. **`indep_paths.txt` の実内容**：FMP3 実レイアウトに合わせた確定リスト（`cfg` の配置含む）。
5. **default ブランチ**：最新メジャー追従で良いか。
6. **派生版の取込方式**：`submodule` / `git subtree` / vendor import script のどれを一次とするか（本流計画は submodule 前提）。
7. **pin 単位**：非依存部 `v3.M.N` タグ単位か、全ツリー `snapshot` タグ単位か。
8. **FMP3 版 cfg の Python 化範囲**：`cfg/` 全体を派生版で置換するか、一部パスに限るか（アーカイブ側は原 cfg を非依存部として保持し、置換は派生版側）。

## 13. 新規リリース時の運用フロー（定常）

1. 公開パッケージを取得し `RELEASES.csv` に1行追記（日付・種別・版・ターゲット・元ファイル名）。
2. メジャーが上がるなら `release/3.(M+1)` を前 tip から分岐。
3. `import_fmp3.sh` を種別に応じて実行（indep / simple）。
4. §9.2 の diff 検証。
5. `git push --follow-tags`。
